十、事务

ACID 四特性：Atomicity 原子、Consistency 一致、Isolation 隔离、Durability 持久。

并发 3 问题（严重度递减）：脏读 → 不可重复读 → 幻读。

4 个隔离级别（性能递减、安全递增）：

级别 脏读 不可重复读 幻读

Read Committed ❌ ✅ ✅

基础篇总览

进阶篇 & 面试高频（⭐ 复试 / 求职必背）

以下为 MySQL 面试 100% 覆盖的进阶知识点，结合 InnoDB 存储引擎展开。

一、索引（Index）

为什么要用索引

索引本质是「空间换时间」的排序数据结构，目的是加速 WHERE 条件匹配 + JOIN + ORDER BY + GROUP BY，把 O(n) 全表扫描降为 O(log n) 级别的查找。

底层数据结构：为什么 InnoDB 选 B+ 树

数据结构 问题
哈希表 只能等值查询，无法范围查询 / 排序 / 分组
二叉搜索树（BST） 极端情况下退化成链表 O(n)
AVL / 红黑树 树高过高，磁盘 IO 次数太多（树高 = IO 次数）
B 树 多叉降低高度，但每个节点存数据，横向扇出不够；且范围查询需要中序遍历回跳
B+ 树（InnoDB 默认） ① 多叉矮胖，树高一般 3-4 层就能存千万级数据；② 非叶子节点只存「键 + 指针」，单页能装更多键，扇出大，IO 少；③ 叶子节点用双向链表串联，范围查询只需顺序扫描，无需回溯

面试口述题：B 树与 B+ 树的区别 → 非叶子节点是否存数据 / 叶子是否链表 / 范围查询效率。

聚簇索引 vs 非聚簇索引（二级索引）

类型 叶子节点存什么 一张表能有几个
聚簇索引（Clustered） 存完整的整行数据 1 个（默认主键建；没主键选唯一非空；都没有自动生成 ROW_ID）
非聚簇索引 / 二级索引（Secondary） 存索引列的值 + 主键值 N 个

由此引入两个高频术语：

  • 回表：先通过二级索引找到主键 → 再用主键去聚簇索引里找完整行 → 两次 B+ 树查找
  • 覆盖索引：查询的列刚好全都在二级索引里（如 SELECT id,name FROM user WHERE name='xxx'，name 是二级索引，id 是主键，叶子里都有），不需要回表，性能最好。

最左前缀原则（联合索引）

联合索引 (a, b, c)，B+ 树按 a→b→c 顺序排序，查询条件必须从最左列开始且不能跳过中间列才能用上索引：

查询 能用到索引的部分？
WHERE a=1 ✅ 用到 a
WHERE a=1 AND b=2 ✅ 用到 a,b
WHERE a=1 AND b=2 AND c=3 ✅ 全用到
WHERE b=2 AND c=3 ❌ 跳过了最左 a，全表扫
WHERE a=1 AND c=3 ✅ 只用到 a（中间 b 跳过了，c 用不到）
WHERE a>1 AND b=2 ✅ 只用到 a，范围之后的列失效
WHERE a=1 AND b LIKE '张%' AND c=3 ✅ 用 a,b；LIKE 前缀匹配可以，%张 后缀不行

常见索引失效场景（面试背）

  1. 索引列上做函数 / 计算 / 类型转换（如 WHERE YEAR(create_time)=2026 / WHERE id+1=5）
  2. 字符串列不加引号，发生隐式类型转换（如 WHERE phone = 13800000000，phone 是 VARCHAR）
  3. LIKE 以 % 开头（后缀匹配 / 中缀匹配），只能前缀匹配走索引
  4. OR 两边有一边没建索引 → 全表扫；给两边都建上才可
  5. **NOT IN / != / <>**：多数情况不走，改 IN 或范围
  6. 联合索引不满足最左前缀（见上表）
  7. MySQL 优化器认为走索引比全表扫还慢（表很小、或 WHERE 命中一半以上数据时），会主动放弃索引

二、EXPLAIN 慢查询分析

定位慢 SQL 第一步：EXPLAIN + SQL 语句，重点看以下列：

列 关注什么 好 / 坏
id 查询执行顺序，大的先执行，相同 id 从上到下 —
**type**（访问类型） 从上到下性能递减：system > const > eq_ref > ref > range > index > ALL ✅ 至少要 range 以上，**ALL 是全表扫必须优化**
possible_keys 可能用到的索引 —
key 实际用的索引 ✅ 不能为空（没有用索引）
key_len 用了联合索引多少字节（越长说明用的列越多，越精准） ✅ 越长越好，结合联合索引最左前缀算
ref 索引列与谁比较（常量 const / 字段） —
rows 预估要扫描的行数 ✅ 越小越好，和实际结果比差很多说明统计信息不准，ANALYZE TABLE
filtered 通过条件过滤后剩下比例 ✅ 高好（90%+），低说明 WHERE 条件不精
**Extra**（关键！） Using index（覆盖索引 ✅） / Using where（服务器层再过滤，不好） / Using filesort（排序没用上索引，要优化） / Using temporary（用了临时表，GROUP BY 没索引，很危险）

面试话术：我一般先 type 看是不是 ALL，再看 key 是否走了预期索引，最后看 Extra 里有没有 filesort / temporary。

三、MVCC 多版本并发控制（为什么 RR 基本解决幻读）

MVCC = Multi-Version Concurrency Control，是 InnoDB 在 Read Committed / Repeatable Read 两个隔离级别下，实现「读不加锁、读写不冲突」的核心机制。

三大基石

组件 作用
隐式字段 每行除了业务列，InnoDB 还藏了 DB_TRX_ID（最近一次修改的事务ID）、DB_ROLL_PTR（回滚指针，指向 undo log 里的上一个版本）
undo log 版本链 每次 UPDATE/DELETE 都会把旧版本写到 undo log，通过 DB_ROLL_PTR 串成一条链 → 一条记录存在多个历史版本
ReadView（读视图） 事务在「第一次 SELECT」的瞬间生成的快照，决定能看到哪些版本。含 4 个字段：m_ids（当前活跃未提交事务ID 列表）、min_trx_id / max_trx_id、creator_trx_id

可见性算法（版本链遍历）

从当前行最新版本开始，顺着 undo log 链往前找，第一个满足以下条件的版本就是你能看见的：

  1. 该版本的 DB_TRX_ID < min_trx_id → 这个事务在生成 ReadView 之前就提交了，可见 ✅
  2. 该版本的 DB_TRX_ID 在 m_ids 列表外，且 < max_trx_id → 生成 ReadView 时已提交，可见 ✅
  3. 该版本 DB_TRX_ID == creator_trx_id → 就是你自己改的，可见 ✅
  4. 否则都不可见，继续往前找。

RR vs RC 的核心区别：ReadView 生成时机

隔离级别 ReadView 何时生成 效果
Read Committed 每一次 SELECT 都生成一个新 ReadView 别人在你事务期间 commit，你下一次 SELECT 就能看见 → 产生不可重复读
Repeatable Read 第一次 SELECT 生成一次，后面一直复用 事务期间 ReadView 不变 → 哪怕别人 commit 了，你也看不见 → 解决不可重复读 + 配合 Next-Key Lock 基本解决幻读

为什么是「基本解决」？因为 MVCC 只管快照读（普通 SELECT）；当前读（SELECT ... FOR UPDATE / UPDATE / DELETE / INSERT）是加锁读，幻读由 Next-Key Lock（Gap Lock + Record Lock） 保证。

四、锁机制

粒度分类

锁粒度 说明 引擎
表级锁 锁整张表，开销小、加锁快、粒度粗、冲突高 MyISAM / InnoDB（LOCK TABLES / DDL 时自动）
行级锁 锁具体行，开销大、加锁慢、粒度细、冲突低 InnoDB
页级锁 介于之间 BDB（已弃用）

InnoDB 的三兄弟行锁（⭐）

名称 锁住什么 出现条件
Record Lock（记录锁） 单条索引记录 用主键 / 唯一索引精准命中一行，且 RR 下
Gap Lock（间隙锁） 两条索引记录之间的开区间空隙，不包含记录本身 RR 隔离级别下，范围查询 / 没命中索引时；目的：防止其他事务往间隙里 INSERT 插入新行 → 解决幻读
Next-Key Lock（临键锁） Record Lock + Gap Lock，即 (左开右闭] 区间，包含最后一条记录 RR 默认；锁住「记录 + 它前面的间隙」

面试经典问：InnoDB 如何解决幻读？
答：RR 级别下，快照读由 MVCC 版本链保证；当前读由 Next-Key Lock（GAP + Record）防止新行插入间隙，两者共同作用解决幻读。

意向锁（表级，和行锁共存不冲突）

  • IS（意向共享） / IX（意向排他）：表示「我这个事务打算给某些行加 S / X 锁」
  • 作用：在加表锁前快速判断有没有行锁冲突，不用逐行检查，O(1) 搞定。
  • 意向锁之间全部兼容（IS/IX 可以共存）；意向锁只和表级 S/X 冲突。

常见死锁场景与避免

  • 场景：事务 A 锁 id=1 → 想拿 id=2；事务 B 锁 id=2 → 想拿 id=1，互相等对方释放。
  • MySQL 自动检测，回滚代价最小的那个事务（show engine innodb status 查看最近一次死锁信息）。
  • 避免：① 不同事务访问相同资源尽量按固定顺序；② 尽量用索引缩小锁定范围，少全表扫；③ 长事务拆短，减少锁持有时长；④ 热点数据用乐观锁（CAS：UPDATE t SET x=x+1, version=version+1 WHERE id=? AND version=?）。
